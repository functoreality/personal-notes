# 笔记发布前风险检测

在把个人笔记公开发布到 GitHub 之前，对笔记做一次风险扫描。
目标是找出公开后可能给作者带来实际损伤的内容，避免意料之外的风险。

## 扫描范围

用户指定文件或范围时，按用户指定的范围扫描。
用户只调用本 Skill、没有附加说明时，立即扫描当前 Git 仓库中
工作树里存在、尚未被 Git 跟踪，且其路径从未出现在 Git 历史中的文件。
无需先询问扫描范围。

先用 `git status --short --untracked-files=all` 找当前未跟踪的候选文件，
再逐个用 `git log --all -- <路径>` 排除曾在 Git 历史中出现过的路径。
已跟踪文件的未提交修改、暂存的改名或修改，均不属于默认范围。
Git 忽略的文件不在默认范围内，除非用户明确指定。
若没有符合条件的文件，直接说明没有可扫描的文件。

文件较多时，可按文件分批，并按需交给子 Agent 阅读和排查。
每个文件仍须完整读取；最后汇总结果，避免重复报告。

## 核心原则

只报告「公开后可能造成实际损伤」的内容，其余一律不报告。

实际损伤指的是：
- 账户或财产安全受损，例如密钥、密码、令牌泄露
- 个人身份或隐私暴露，例如真实姓名、电话、住址被公开
- 他人隐私被公开，给第三方带来伤害或纠纷
- 私下交流内容被公开，破坏信任关系
- 明确的工作或机构保密信息被公开

判断标准始终是：公开后会不会给作者带来实际损伤。
不在这条线上的内容，不管看起来如何，都不要报告。

## 不需要报告的内容（负面清单）

以下内容一律不视为风险，不要报告，也不要向作者确认：

1. 模型名称、版本号、工具名称。
   作者是普通用户，没有内测资格，接触不到保密信息，
   模型和工具的评测对比不构成泄密。
2. 科研或学术相关内容。
   这不是科研笔记，不含任何作者打算日后发表的内容，
   不涉及抢先或原创性问题。
3. 错别字。
4. 过时的信息、已经失效的链接。
   作者不追求信息有效性，只追求公开后不带来意外风险。
5. 网上可以公开查到的一般信息。
   除非有明确标注说明来自私下渠道，否则默认来自网上公开信息。
   但作者针对公开内容产出者的不友善评价，适用必报清单第 6 类。
6. 文风、质量、结构、排版等写作层面问题。
   这些与风险无关。

## 需要报告的内容（必报清单）

以下内容一旦出现，应当报告。每类都要给出具体位置和原文引用。

### 1. 凭据与密钥

- API key、token、密码、cookie、私钥、访问密钥、数据库连接串等。
- 这是最直接的损失来源，一旦出现必须报告。
- 示例：出现 `sk-xxxx`、`password=xxx`、`Bearer xxx` 这类内容。

### 2. 个人身份与隐私

- 真实姓名、手机号、住址、身份证或护照号、学号或工号、银行卡号、
  私密邮箱等可定位到作者的信息。
- 健康、财务、家庭等敏感个人情况。
- 判断标准：公开后是否可能被用来定位或联系到作者本人，或造成身份盗用。
- 注意：作者自己使用的笔名或公开身份不在此列。

### 3. 他人隐私

- 笔记中提到的具体他人的真实姓名、联系方式、隐私细节。
- 未经对方同意公开，可能给对方带来伤害，也可能给作者带来纠纷。

### 4. 私下交流内容

- 明确标注来自私下渠道的内容，判断规则见下一节。

### 5. 明确的工作或机构保密信息

- 属于所在机构、公司、实验室的内部保密信息，
  例如未公开的数据、未发布的项目细节、内部系统信息。
- 注意：作者自己的方法论和经验总结不属于此类，不要扩大化。

### 6. 针对可识别对象的不友善评价

- 针对可识别的人，或可对应到具体作品、项目、机构的主观贬损、
  嘲讽或不友善评价。
- 即使被评价的对象和原始材料均来自公开渠道，也应报告。
  风险不在于公开信息本身，而在于评价可能损害作者的合作关系、
  社群关系或声誉。
- 只指出可验证的事实、方法局限或实验缺口，不属于此类。
- 对通用事物的批评，以及对自己的困惑或自我批评，不属于此类。
- 此类以「可能影响关系或声誉，请确认是否保留」的口吻提醒，
  不要断言一定会造成损失。

### 7. 其他可能造成实际损伤的内容

上面的清单不是穷尽的。如果在笔记中看到上面没列出来、
但你判断公开后可能给作者带来实际损伤的内容，
也应当提出来，说明理由，并询问作者是否真的会造成影响。

这一类属于「不确定是否真的要报」，所以用提问的方式提醒，
而不是直接断言为风险。

## 私下交流的判断规则

默认假设：笔记内容都来自网上公开信息，除非有明确标注说明来自私下渠道。

以下标注说明来自私下渠道：

- 朋友圈、当面交流、面谈、口述
- 私下交流、私聊、私信
- 微信聊天、群聊、电话沟通
- 「某某告诉我」「某某说」且指向具体私下场合
- 「日期 + 人名」，例如 `from 2025-02-24 张三`。
  网上公开看到的信息一般只放链接、不记「什么时候看到的」，故这种写法多半是私下讨论

没有这些标注的，一律按公开信息处理，
不要推断「这看起来像是私下交流」。

确认是私下交流后，是否报告取决于能否定位到具体的人：

- 只是缩写（如 `lyp`）且无法推断出具体是谁，不算风险，不报告
- 例外：内容涉及个人身份等敏感信息（不是纯粹讨论做事的方法），即使用了缩写也仍要报告
- 讨论做事方法的内容，公开读者看不出是谁说的，即可接受，不报告

## 报告格式

先完整读取笔记内容。
通常不必借助 outline-read 之类的工具按层级折叠阅读，
因为你不需要梳理笔记的逻辑结构，只需要对各个具体的信息点分别排查是否构成风险。
分多个连续小段依次阅读是可以的。

然后扫描，报告格式如下：

- 没有发现任何需要报告的内容时，直接说「未发现需要重点关注的内容」。
- 发现时，按类别列出，每一条包含：
  - 位置：行号或原文引用
  - 类别：属于上面哪一类，若不属于清单则标注为「其他」
  - 风险说明：公开后可能造成的具体损伤
  - 建议：如何处理，例如删除、脱敏、或请作者确认

对「其他」类，措辞上采用「可能是风险，请作者确认」的口吻，
不要把话说死。

不要为了凑数而报告，也不要长篇大论，只聚焦真正的风险点。

## 报告前的自查

在最终报告之前，逐条问自己：

这条内容公开后，会不会给作者带来实际损伤
（账户安全、身份泄露、他人隐私、私下关系、组织保密）？

- 答案是「不会」的，删掉，不要报告。
- 属于负面清单的，无条件不报。
- 属于必报清单的，直接报。
- 清单之外、但判断「可能」的，作为「其他」提出并询问作者。
